# trace-pipeline-go

一套**完全本地运行**的追踪、日志聚合与告警评估流水线：用内存数据结构与单进程并发
模拟多组件协作，不依赖任何外部服务或凭据。重点保证并发与异常场景下的观测结论
**一致、可解释、可验证**。

仅使用 Go 标准库（`go.mod` 无第三方依赖），要求 Go 1.25+。

## 包结构

| 包 | 职责 |
| --- | --- |
| `trace` | 关联标识生成与传播、请求范围内一致的采样决策、并发安全的 span 记录 |
| `logpipe` | 有界缓冲、多生产者并发写入、按关联标识聚合、三种可区分的背压拒绝原因 |
| `alert` | 对齐时间窗口的规则评估、乱序容忍、去重与跨窗口抑制、规则版本化与历史复现；关键输入持久化记录、跨进程还原与压缩 |
| `cmd/demo` | 串联三大能力的本地演示 |

## 1. 关联标识（Correlation ID）的生成与传播规则

- 标识格式：`cp-<UnixNano>-<进程随机后缀>-<进程内原子序列>`。
  - 原子序列（`sync/atomic`）保证同一纳秒内大量并发调用也**不会重复**；
  - 进程随机后缀（启动时 `crypto/rand` 生成）避免多进程时钟相同时撞号；
  - 入口接收外部标识时可用 `trace.NewIDFrom(existing)` 沿用而不重新生成。
- 传播载体是标准 `context.Context`：
  - **同步调用**：`trace.WithContext` 放入、`trace.FromContext` 取出，随调用链自然传递；
  - **异步任务**：必须使用 `trace.Detach(ctx)`——它保留父 ctx 的全部 Value
    （关联标识、采样决策），但脱离父 ctx 的取消与截止时间，因此父请求结束/取消
    不会中断异步任务，也不会让关联标识丢失；
  - **错误链路**：span 以错误结束时被标记为 `KindError`，但其关联标识不变。
- span 模型（`trace.SpanRecorder`，互斥锁保护）：一次请求内所有 span 共享同一个
  关联标识 `Span.ID`；每个 span 另有独立唯一键 `SpanKey` 作为自己的身份，
  `Parent` 指向上游 span 的 `SpanKey`——**关联标识不串号，节点身份不混用**。
- 关键不变量（测试覆盖）：N 个 goroutine 并发生成的 ID 全部唯一；
  同步/异步/错误 span 记录中只出现一个关联标识。

## 2. 采样策略

- `trace.NewFixedSampler(rate)`：
  - `rate<=0` 全不采样，`rate>=1` 全采样；
  - `0<rate<1` 时对 Correlation ID 做 FNV-1a 稳定哈希取模。**决策只依赖 ID**，
    因此同一 ID 在同步调用、异步任务、错误链路中、无论被询问多少次，结论恒定，
    不随调用点或时间漂移。
- 请求范围内可用 `trace.EnsureDecision(ctx, sampler)` 把决策缓存进 ctx，
  作为"请求范围内始终一致"的推荐入口；即使不同分支各自首次询问，稳定哈希
  也保证它们得到同一结论。

## 3. 日志聚合与背压策略

- **有界缓冲**：内部是容量为 `Config.Capacity` 的 channel，杜绝无界内存增长。
- **单消费者聚合**：唯一后台消费者从缓冲取条目，按关联标识累加计数；
  多生产者的并发写入与调度顺序无关，聚合结果确定（批次刷新或关闭排空后）。
  刷新触发条件：批大小（`Batch`）、定时间隔（`Interval`）、关闭时强制最终刷新。
- **背压处理，绝不静默丢弃、不阻塞、不死锁**：
  - `TryEnqueue`：非阻塞，失败立即返回带现场（队列长度/容量/待聚合条数）的
    `*RejectError`；
  - `Enqueue`：缓冲满时阻塞等待空位，但受调用方 ctx 约束；
  - 三种**互斥可区分**的拒绝原因（`RejectReason`）：

    | 原因 | 含义 |
    | --- | --- |
    | `buffer-full` | 有界缓冲已满（聚合器未关闭） |
    | `context-done` | 调用方 ctx 在入队前/等待中取消或超时 |
    | `aggregator-closed` | 聚合器已关闭 |

  - 调用方可据原因决策：满了退避重试、ctx 取消则放弃、关闭后不再写。
- **关闭协议（防死锁）**：`Close` 先置关闭位并通知消费者转入"排空模式"
  （持续接收并立即合并，直到队列关闭），然后等待所有在途发送者（含因缓冲满
  而阻塞、正被排空消费者交接的）退出临界区，最后关闭 channel 并等待消费者结束。
  因此高并发阻塞写入下 `Close` 也能在确定时间内完成，且**关闭前已入队条目零丢失**；
  重复 `Close` 安全。
- 可观测计数器：`Accepted()` 成功入队数、`Dropped()` 被拒数（拒绝均显式报错，
  计数仅用于核对），`Accepted + 实际关闭拒绝 = 实际调用次数` 是测试断言的不变量。

## 4. 告警窗口与抑制规则

所有时间判定只依赖事件自身的 `At` 与水位（watermark），不依赖处理墙钟，
因此结论确定、可复现。

- **对齐滚动窗口**：时间轴按规则窗口切成互不相交的桶，
  `bucketStart = floor(At / Window) * Window`，事件按 `At` 归入对应桶。
- **乱序容忍**：
  - 桶未"最终化"前到达的乱序/迟到事件一律接收；判定时桶内事件先按
    `(At, 到达序号)` 稳定排序，再交给纯函数 `EvaluateWindow` 统计（值求和后按
    `>=` / `>` / `==` 阈值比较）——同一批输入无论到达顺序，结论完全一致，
    **不会遗漏也不会重复告警**；
  - 水位通过 `Advance(t)` 显式推进；当 `桶结束时间 <= watermark - lateness`
    时桶被最终化（`lateness` 为构造引擎时设定的可容忍乱序时间）；
  - 最终化之后才到达、目标桶已永久关闭的事件返回包装 `ErrTooLate` 的
    `*LateError`（携带涉及规则与当前水位），**显式拒绝而非静默丢弃**。
- **去重与抑制**：
  - 桶只在最终化时判定一次，`(规则版本, 桶)` **至多产出一条告警**；
    重复推进水位不会重复告警；
  - `Rule.Suppress>0` 时启用跨窗口抑制：同一规则自上一次实际触发的桶起，
    在 `Suppress` 时长内的后续命中只记录为 suppressed、不告警，抑制结论
    同样可通过 `History` 查询，做到"命中可解释"。
- **规则变更与历史复现**：同 ID 规则定义变化（指标/算子/阈值/窗口/抑制）时
  `AddRule` 自动产生新版本；新事件只进入当前版本，旧版本的窗口状态、
  触发/抑制/最终化记录与告警完整保留。`Engine.History(ruleID)` 返回全部版本的
  `VersionHistory`；`EvaluateWindow` 是无副作用纯函数，任何历史窗口都可以
  用"规则 + 事件集合"离线重放，结论一致。

## 5. 评估结论的持久化、还原与压缩（alert.Recorder）

`alert.Recorder` 在 `Engine` 外面包了一层"先算后记"的记录能力：评估结论不再只留在
内存里，换进程或重启后只靠磁盘上的记录即可**逐字段**还原当时的结论——**不需要
调用方再传任何设置值**。

### 为什么记录可以脱离调用方传的设置值独立还原

评估结论唯一依赖的"设置"是乱序容忍 `lateness`（它决定最终化线
`watermark - lateness`，进而决定哪些桶关闭、哪些迟到事件被拒）。因此创建记录目录
时，`lateness` 被当作**第一条日志记录**（`config`）落盘，压缩产生的快照里也存了
同一份值。打开记录时一律以录进去的值为准：

- 传了和当初不一样的值：被忽略，还原用的是记录里的值；
- 完全不传：同样可以打开，`OpenRecorder(dir)` 的 `lateness` 参数是可选的，
  只有**全新目录**才用传入值（缺省 0）创建并落盘。

除此之外，结论只由"事件 + 规则变更 + 水位推进"的先后顺序决定，而这些输入全部
按实际生效顺序记录在案（见下），所以"录进去的是什么，还原出来就是什么"。

### 记录里保留了什么

记录目录下有两类文件（均为 JSON，无外部依赖）：

- `journal.log`：追加式日志，每行一条记录，按发生先后带单调递增 `Seq`：
  - `config`：评估设置（`lateness`），创建目录时的第一条记录；
  - `rule`：一次生效的 `AddRule`（记录调用方原始定义；版本号重放时由同一套
    `AddRule` 逻辑重新推导，还原不走另一套计算）；
  - `event`：一次 `Observe`。**不带时间戳的事件在记录前已按当时水位补齐**，
    日志里存的是实际生效值；被部分规则判迟到（`ErrTooLate`）的事件也照实记录，
    重放时同一逻辑做出同一拒绝；
  - `advance`：一次水位推进（记录调用方请求的目标时间）。
- `snapshot.json`：压缩产生的基线——某 `Seq` 处引擎状态的完整镜像（评估设置、
  水位、事件到达计数器、每规则每版本的窗口桶与到达序号、最终化/触发/抑制标记、
  已产出告警、抑制游标）。

### 按什么顺序还原

`OpenRecorder(dir, lateness...)`：

1. 有快照则先整体恢复快照状态（评估设置取自快照）；
2. 无快照则先流式扫描日志找到 `config` 记录，以其设置值建引擎；
3. 流式重放日志：**跳过 `Seq <= 快照Seq` 的记录**与 `config` 记录，按序把其余
   记录重新作用到引擎（重放与在线写入共用同一条代码路径）。

因为所有变更操作都在同一把互斥锁下"先改引擎、再写日志"，日志顺序就是引擎实际
的评估顺序：不带时间戳的事件与水位推进、并发写入任意交错，还原结论都与在线
逐字段一致（触发/抑制/最终化集合、每条告警的值/关联ID/触发时间）。只有原始
记录、或已有压缩基线（快照+增量），两条路径还原出的结论完全相同。

### 规则改定义前后的历史怎么兼容

规则变更只产生新版本（见第 4 节），日志按时间顺序记录每次 `AddRule`；重放到
变更点之前的输入仍落在旧版本状态上，变更点之后落在新版本上，旧版本的触发/
抑制/最终化结论完整保留，新定义不会污染旧结论。快照则把每个版本的窗口状态
分别整体镜像，压缩也不丢版本历史。

### 容量与压缩策略

日志文件随写入量线性增长（磁盘），但**进程内存不随累计写入量增长**：

- `FileJournal` 不在内存里缓存任何记录：打开/重放是流式扫描（逐条读出、
  逐条释放），截断时也只把"要保留的增量"从磁盘流式读出再原子重写；
- 引擎里桶一旦最终化即永久关闭，桶内事件立即释放——内存只随"未最终化窗口"
  的规模（由 `lateness` 与在途事件决定）增长，长时写入下保持平稳；
- 重启后重新打开再大的日志，重放同样是 O(1) 常驻内存。

日志不能无限增长，用 `Recorder.Compact()` 把当前状态写成快照基线，再把日志
截断为快照之后的增量：

1. 持锁做纯内存的状态镜像并记下日志序号（极快）；
2. **锁外**写快照文件（先写 `.tmp` 再 rename，崩溃不会留下半截文件），
   写入方不被这段 I/O 阻塞；
3. 持锁把日志中 `Seq <= 快照Seq` 的部分原子重写掉——压缩期间新写入的记录
   序号更大，全部保留，**不丢记录、不卡死写入方**。

失败与重试安全：压缩在任一步失败都不会同时改动快照和日志；重试只是基于当前
状态重算一次。即使崩溃留下"快照较新、日志仍含旧记录"的重叠现场，恢复时按
`Seq` 跳过重叠部分即可——不重复计数、历史不错乱。

### 本地一步步验证

```bash
# 逐字段还原（含规则中途改定义、零时间戳事件、迟到拒绝）
go test -race -v ./alert/ -run TestReplayReproducesConclusionsFieldByField

# 打开时传错设置值 / 完全不传：纯原始记录与快照+增量两条路径还原均一致
go test -race -v ./alert/ -run TestRestoreIndependentOfCallerLateness

# 零时间戳事件 × 水位推进 × 并发写入：任意交错下结论稳定
go test -race -v ./alert/ -run TestConcurrentUntimestampedInterleavedStable

# 压缩前后结论一致、压缩期间并发写入不丢
go test -race -v ./alert/ -run TestCompactionPreservesConclusions

# 压缩失败重试 / 崩溃重叠现场恢复，结论不变
go test -race -v ./alert/ -run TestCompactionFailureRetryKeepsConclusions

# 并发写入 × 多轮压缩 × 注入失败重试 交错：不丢记录、结论不变
go test -race -v ./alert/ -run TestCompactInterleavedWithWritesAndFailures

# 长时写入内存不线性增长、重启重开记录内存回落
go test -race -v ./alert/ -run TestMemoryDoesNotGrowWithCumulativeWrites

# 全部测试（含既有用例）带竞态检测多跑几遍
go test -race -count=5 ./...
```

测试日志（`-v`）会打印每个场景的关键输入（事件、规则版本、水位推进）与判定
依据（触发/抑制/最终化集合、告警内容、压缩前后文件大小、堆存活字节数），
可直接核对结论为什么成立。

## 6. 本地验证方法

```bash
# 编译与静态检查
go build ./...
go vet ./...

# 全部单测 + 集成测试（-race 检测数据竞争）
go test -race ./...

# 查看关键输入与判定依据（测试内 t.Logf 已打印）
go test -race -v ./...

# 端到端演示（无外部依赖）
go run ./cmd/demo
```

测试覆盖一览：

- `trace`：2000 goroutine 并发生成 ID 无重复；同 ID 采样决策 1000 次恒定；
  集成测试验证同步/异步/错误链路共享同一 ID。
- `logpipe`：150 生产者小容量（4）并发写入 3000 条，聚合计数确定且零丢失；
  三种拒绝原因逐一断言且互不混淆；64 goroutine 阻塞式 `Enqueue` 与 `Close`
  并发进行，5 秒内完成且"成功入队 + 关闭拒绝 = 实际调用数"无缺口；
  关闭后排空无丢失、重复关闭安全。
- `alert`：阈值触发且重复推进不重告；乱序到达与顺序到达结论一致；
  最终化后迟到事件返回 `ErrTooLate`；跨窗口抑制精确到桶（10:00 触发、
  10:01/10:02 抑制、10:03 再触发）；规则变更后 v1 历史结论保留且不被
  新事件污染；纯函数对不同排列输入结论恒定；50 goroutine 并发投递 10 个桶，
  每桶计数精确无丢失/串桶；关键输入落日志后换进程还原逐字段一致；
  打开记录时传错/不传设置值，纯原始记录与快照+增量两条路径还原均一致；
  零时间戳事件与水位推进/并发写入任意交错不丢不重不串窗口；
  压缩前后及失败重试后结论与不压缩对照完全一致；
  并发写入 × 多轮压缩 × 注入失败交错不丢记录；
  长时写入下内存不随累计写入量线性增长，重启重开记录内存回落。
- 根包 `integration_test.go`：同一关联标识贯穿 span、日志聚合与告警，
  三处观测结论可互相核对。
